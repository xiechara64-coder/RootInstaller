# v1.2.0

新增 **同签名提示**：同一个签名、同一个应用名称、**但包名不同**的安装包会被标出来。
这类包不能互相覆盖，会作为两个应用共存 —— 最常见的坑是「作者改了包名，
你以为在升级，结果装出第二份」。

## 新增

### 列表徽标

行末加 `· 同签名×1`，直接把「这个包和另一个同名同签名的包并存」摆出来。

### 详情页说明

一节「同签名但包名不同的安装包（N）」，列出具体包名，并说明：

> 覆盖安装要求「包名相同且签名相同」，所以这些包和当前这个不能互相覆盖，
> 会作为独立应用共存。如果作者改过包名，你以为在升级，装完却会多出一份，
> 数据也不会自动迁过去。

截图（真机）：两个 Minecraft —— `com.mojang.minecraftpe1532` 1.5.3.0 与
`com.mojang.minecraftpe` 1.2.0.81，都装着、都带 `同签名×1`。

## 判据：签名 + 应用名称

**第一版只比签名，结果翻车了**：这台设备上 151 个包里有 **140 个**被判定为
"同签名不同包名"——厂商系统应用共用同一个平台签名。140 次提示等于没有提示，
真正的"改包名"案例被埋在噪音里。

加上第二条判据「**应用名称相同**」（去首尾空白、压缩内部空格、忽略大小写）后，
结果从 **140 降到 2**，正好是真该提醒的那一对。

> 这就是为什么不能图省事：只看签名，这个功能等于不存在。

## 成本：只在第一次扫描时付

列表扫描**不读签名**（会拖慢首屏）。列表显示后由后台线程补证书：

| | 第一次（缓存无证书） | 之后 |
|---|---|---|
| 补齐耗时 | **59 秒 / 151 个包** | **0 个 / 1 毫秒** |
| 来源 | 逐个读签名块 | 解析缓存新增的 `certSha1` 字段 |

补完写回解析缓存（缓存格式升到 v3），所以只有第一次要等，且不挡列表。

实现上分成两条路径：
- 分组只要「谁签的」→ `ApkSignatures.inspectCertificate()`（不跑 v1 摘要链核对）；
- 详情页要「内容有没有被改过」→ 原来的 `inspect()`（完整校验）。

## 其它

- 离线用例 12 → **13 组**，新增 `SameSigGroupsCheck`（19 条断言）：
  同签名同名称才算一组、同签名不同名称不报（就是上面那个 140→2 的教训）、
  名称规范化、同包名去重、缺证书/缺名称不参与、两组互不影响、边界输入。
- 构建脚本的 javac 堆上限从 512 MB 降到 **320 MB**：在本机（可用内存只剩
  424 MB）实测 512 MB 会以 `malloc failed: Chunk::new` 失败，320 MB 能过；
  CI 上 320 MB 也足够。

## 升级说明

- 与 v1.1.0 **同签名**，直接覆盖安装即可。
- 升级后**第一次扫描会慢一些**（解析缓存格式升级 + 后台补证书约 1 分钟），
  之后恢复正常；补证书在后台，不影响列表使用。
